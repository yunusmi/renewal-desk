# Reliability — normative execution contract

## Guarantees and boundaries
Durable acceptance and at-least-once processing, one local business effect, one provider operation **while its idempotency store remains intact**. HTTP requests may repeat. No global exactly-once claim. Provider is in-memory, restarting it erases evidence. No DB transaction spans HTTP; no in-memory timer is sole source of retry/recovery. Do not auto-replay a completed request. A confirmed provider result and failed local invariant must not be represented as failed external operation.

## Commands (transactions)
Create: authenticate and authorize initiator, resolve resource, enforce tenant, lock resource `FOR UPDATE`, read snapshot, create request+audit in same transaction. DB partial unique index is final race defense; on uq violation rollback and 409 `active_renewal_exists`. Dates from snapshot `DATE + 30`. Return only committed result.

Approve: authorize approver workspace; lock request then resource; self-decision 403 before business mutation; status must pending; compare current expiry, amount, currency with snapshot; mismatch 409 `resource_changed`. Update conditional status, decided_by/time, initialize provider_confirmation pending; insert unique job with exact stored payload/key reference and phase post/queued, next_run_at=now; insert approval and enqueue audit; commit. Return processing. On job/audit insert error rollback whole command. No external call in API. Concurrent approve/reject: only one committed transition, second 409. Reject: same permissions and request lock/status; rejected/decision fields/audit in one transaction, no job, no expiry changes, no provider.

Retry: approver tenant, lock request → resource (if needed) → job; request requires_attention only. Same request/job/key/payload; status processing; phase check; reset post_attempts=0, preserve total, clear reason for current run, invalidate old lease (increment token), queued/next_run_at now; audit retry. Preserve already confirmed operation evidence and `provider_confirmation=confirmed` when known; otherwise uncertain. No new job. Concurrent retry one success, second 409. Own-approval prohibition applies to approve/reject, not retry previously approved by another user (explicit design decision). If request was attention due to local mismatch, retry does not force-update resource or POST after known confirmation.

## Claim and recovery
Worker loop: short poll interval (e.g. 500ms, configurable); claim queued ready jobs or leased jobs whose lease expired using DB clock and `FOR UPDATE SKIP LOCKED`. Claim in one short transaction; set leased, increment monotonically increasing `lease_token`, set `lease_until`. Return token. Release lock before any HTTP. Lease duration greater than HTTP timeout + write margin (e.g. 30s vs 5s; validate configs); if needed renew using same token, no indefinite lease. Never process terminal jobs. Worker graceful shutdown stops claiming, finishes bounded in-flight operations or leaves lease for recovery. Restart automatically polls and recovers without manual reset.

**Fencing**: every worker mutation (reserve attempt, record response, schedule, finalize, mark attention, audit) must in a transaction lock/check current request/job and verify `status=leased`, lease_token matches and lease still valid using DB clock. Stale worker must discard its result and never write state/audit. A stale HTTP call may still have happened; same key/payload handles effect. Claims never hold job lock while acquiring request/resource. Finalize lock order request→resource→job; other mutations request→job; if no resource needed skip. Release/renew with matching token. Lease expiration after call causes recovery via GET. Multiple workers safe.

## Persistent execution phases
Job status queued/leased/done/attention, phase post/check. `next_run_at`, lease, counter, last_attempt_at and last_error_code persisted. Request provider_confirmation pending/uncertain/confirmed/not_confirmed. One job per approved request, no new row for retry. Store operation_id only after validated result; use stable request key, exact immutable 4-field payload.

### POST
1. First claim phase post, no uncertain previous attempt. In short fenced transaction reserve a possible POST slot (`post_attempts++`, `post_attempts_total++`, `last_attempt_at=now`, phase check, persist earliest reconciliation time = now + delay, audit attempt_reserved/provider_post with outcome pending). If counter already 3, do final GET rather than POST. Commit before network. Send POST using stored key/payload and timeout. Disable implicit HTTP client retries/redirects, count all POST sends explicitly.
2. 200 completed with valid response → finalize. 503, timeout, connection failure or transient 5xx → uncertain, audit sanitized outcome, queue phase check, next_run_at = DB now + configured RETRY_DELAY_MS, release lease. No immediate POST. Any response-loss crash before persisting is covered by precommitted phase check and lease recovery; wait until next_run_at and lease expiry as applicable.
3. 409 key conflict or definite permanent 4xx/invalid successful body → attention with explicit reason, no new key/no automatic blind POST; optionally reconcile GET for evidence if safe. The 3-attempt rule applies to unresolved transient results; permanent conflicts stop early. Do not classify 503 as rejection. 429 use bounded delay (optional Retry-After with cap), same ambiguity policy.

### GET reconciliation
- On recovery of previously reserved attempt, after 503 delay, and on manual retry: GET `/renewals/{encodeURIComponent(key)}`. GET does not increment POST counters. 200 valid completed → finalize. 404 or transient error: when slots remain, queue phase post with bounded delay, same payload/key. If no slots remain, mark requires_attention after final GET attempt. Do not busy-loop GET indefinitely; bounded GET per cycle/phase, any optional additional GET retries separately counted and finite. 409/invalid response/permanent error → attention. If already have valid confirmed operation evidence (local invariant mismatch), do not issue additional POST; use GET/recorded verified evidence to attempt local finalization only; if provider no longer recognizes key, retain recorded confirmation, report discrepancy, attention, no unsafe recreation.
- Lease recovery of a job that has never reserved a POST can use phase post. When recovering phase check, reconcile first even if post_attempts==3. Do not lose the final GET because of the counter. `next_run_at` persists across restart; after expiry, delayed work becomes eligible. Manual retry starts with GET, including when previous failure had no confirmed operation.

### Crash accounting tradeoff
Cannot atomically commit a DB counter and an external HTTP send. A process can crash after durable reservation but before bytes leave; count this as **possibly sent** (conservative POST budget). The UI label/tooltip and docs distinguish reservations/attempts, actual known outcomes, and total; test this crash window explicitly. After restart reconcile first; if no provider record and slots remain, schedule another reserved POST. If the third slot is ambiguous, perform GET before attention; do not silently mark exhausted without reconciliation, and do not send an untracked fourth POST to compensate. Manual retry can open another cycle. No claim that every reserved slot definitely reached provider. This is a documented compromise to bound automatic attempts; no distributed transaction with external HTTP. Persist attempt history including reserved/outcome unknown vs actual response, not fabricated outcomes.

### Validate provider response
Require HTTP 200 JSON object, nonempty valid operation_id (UUID as simulator returns), status exactly completed, started_count exactly integer 1, resource_id, period_months exactly integer 1, amount_minor and currency equal immutable payload. Validate types/fields; no coercion of amounts. Reject conflicting operation_id versus previously confirmed evidence. Store allowlisted fields and timestamps only; do not store/log full raw response or credentials. GET unknown=404; never accept malformed 200 as confirmation.

## Atomic finalization
In transaction lock request, resource, job and fence; if request already completed return no-op (no new audit/date update; a normal stale claim cannot modify it). Only processing + valid job allowed. Compare snapshot current expiry, amount, currency (the latter extra conservative invariant), verify resource/workspace match. If match, `UPDATE resources SET expires_on=:snapshot_new WHERE id=:id AND workspace_id=:ws AND expires_on=:snapshot_previous ...` and require exactly 1 row. Set request completed, provider_confirmation confirmed, operation_id, clear attention reason; set job done, release lease; write confirmed/term_updated events (exact transition once). Commit. No `expires_on += 30` on current date. If mismatch (including current already equals new but request not completed), **do not assume prior successful commit**; record valid provider evidence, mark request/job attention with `resource_changed` and audit in same transaction, leave resource unchanged. Manual correction is outside UI scope; document controlled operator procedure/limits, no unreviewed resource edits. If commit fails all updates rollback; worker will reclaim/reconcile after lease expiry. If process crashes after commit, job done; no new processing. If provider confirmation was valid but DB write failed, GET obtains same evidence on recovery. Any stale result no-op, not 500 to end user.

## Audit types
`request_created`, `request_approved`, `request_rejected`, `job_enqueued`, `provider_post`, `provider_check`, `provider_confirmed`, `term_updated`, `requires_attention`, `retry_requested`; optional `attempt_reserved`/`job_recovered` if reflected in contract/UI. Every domain state transition has actor (user or NULL system), DB time, from/to; sanitized result/detail; do not log entire provider payload/response or idempotency header. UI may display operation key/ID for authorized request and README verification. Key is not auth secret, but avoid logging it routinely.

## Configuration & observability
`PROVIDER_BASE_URL`, `PROVIDER_TIMEOUT_MS=5000`, `RETRY_DELAY_MS=6000` (restart scenario set 20000 or more), `WORKER_POLL_MS=500`, `JOB_LEASE_MS=30000`, `WORKER_CONCURRENCY=1` default (test >=2). Validate positive ranges/lease margin. Structured logs request_id, job_id, status, attempt, error_code, duration, correlation ID; redact secrets, no raw response. Liveness separate readiness (DB/migrations); provider down should not block API accepting work. Document DB/worker health and what `requires_attention` means.
