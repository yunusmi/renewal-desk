# Проверка RenewalDesk: пошаговые сценарии

## Подготовка и аккаунты

Core: **http://localhost:8080**, теперь 18 ресурсов: **15 Alpha и 3 Beta**. Demo: http://localhost:8081, отдельные данные с историческими заявками. Если Core не запущен, включите Docker Desktop и выполните `make up` из корня проекта.

Пароль у всех — `demo1234`:

| Email | Роль / пространство |
|---|---|
| `initiator.alpha@renewaldesk.test` | Создаёт заявки в Alpha |
| `approver.alpha@renewaldesk.test` | Согласует, отклоняет и повторяет обработку в Alpha |
| `universal.alpha@renewaldesk.test` | Обе роли Alpha, но не решает свои заявки |
| `initiator.beta@renewaldesk.test` | Создаёт заявки и просматривает только Beta |

Для смены аккаунта нажмите «Выйти» (на мобильном — внутри «Меню»). Для одновременной проверки используйте два отдельных браузерных профиля или обычное и приватное окно. Вкладки одного профиля разделяют cookie и вход. Cookie localhost также не разделяются по портам, поэтому Core и Demo проверяйте в разных профилях.

Обновлённый seed добавляет недостающие ресурсы, сохраняя ваши заявки, историю и изменённые сроки. В новом Core заявки создаёте вы: фиктивные согласования и операции в него не добавляются. Повторный `make up`/`make seed` не возвращает исходные даты.

Проверяйте каждый сценарий на ресурсе без активной заявки. Если выбранный ниже ресурс уже занят, выберите другой свободный и подставьте его ID. Отклонить оставшуюся pending-заявку можно другим согласующим; автоматически очищать БД не нужно. Перед продлением запишите **текущий срок**, ID заявки и адрес её страницы. Новая дата — текущая +30 календарных дней.

## 1. Вход, неверный пароль, выход

1. Откройте Core. Введите `initiator.alpha@renewaldesk.test` и неправильный пароль, нажмите «Войти».
2. Ожидается понятная ошибка 401, вход не выполнен.
3. Введите правильный пароль `demo1234`: откроется «Обзор», в шапке Alpha и имя инициатора.
4. Нажмите «Выйти», затем откройте `/resources`: ожидается форма входа. Не нажимайте неверный вход много раз подряд — действует ограничение частоты.

## 2. Каталог и изоляция списков

1. Войдите инициатором Alpha → «Ресурсы» → сбросьте фильтры. Ожидается **15 ресурсов**. В «Обзоре» KPI ресурсов тоже 15.
2. Среди них есть базовые «Хранилище A», «Сервис B», базы данных, лицензии, мониторинг, VPN, почта, CI/CD и длинное название корпоративной подписки.
3. Выйдите, войдите инициатором Beta. Ожидается **3 ресурса**: «Сервис C», «Аналитическое хранилище событий», «Лицензии BI-платформы». Данных Alpha в списках/обзоре/истории нет.

## 3. Создание заявки и снимок данных

1. Инициатор Alpha → «Ресурсы» → свободный «Хранилище A» → «Продлить».
2. Проверьте название, стоимость и сравнение дат. На исходном ресурсе: 01.03.2027 → 31.03.2027, 1 280,00 RUB. Если его уже продлевали, используйте текущую дату.
3. Нажмите «Создать заявку».
4. Ожидаются страница новой заявки, статус «На согласовании», автор текущий инициатор и событие создания.
5. **Текущий срок ресурса ещё прежний.** Сумма и даты в заявке не редактируются пользователем.
6. Сохраните адрес заявки для сценариев 4–5.

## 4. Отмена диалогов

1. В отдельном профиле войдите согласующим Alpha и откройте pending-заявку другого пользователя.
2. Нажмите «Согласовать…», затем «Отмена»; повторите через Escape.
3. Ожидается прежний статус «На согласовании», отсутствие события согласования и прежний срок.
4. Аналогично проверьте «Отклонить…» → «Отмена».
5. При создании заявки «Отмена»/Escape тоже не должны создавать новую строку.

## 5. Согласование и штатная неопределённость 503

1. Согласующий Alpha открывает заявку из сценария 3 → «Согласовать…» → «Согласовать заявку».
2. Ожидается «Выполняется». В течение обычной задержки может показываться «Результат операции пока не подтверждён»: провайдер сохраняет операцию, но первый ответ — 503.
3. Не нажимайте ничего повторно; дождитесь «Завершена» (обычно несколько секунд, при остановленном worker дольше).
4. Проверьте текущий срок = новая дата снимка, `operation_id`, ключ операции и события обработки/обновления срока.
5. Обновите страницу несколько раз: срок не должен увеличиваться снова. Кнопок решения для завершённой заявки нет.
6. В «Истории операций» и истории ресурса должны быть согласованные данные.

В терминале можно сравнить статистику **до и после** выполнения:

```sh
curl 'http://localhost:18091/stats?resource_id=res-a-01'
```

Если на ресурсе уже были продления, счётчик увеличивается на **1**, а не обязательно равен 1 всего. Начальный `operation_count=1` ожидается только на ещё не продлевавшемся ресурсе.

## 6. Отклонение без внешней операции

1. Инициатор Alpha создаёт заявку на свободный «Сервис B». Запишите его текущий срок.
2. В терминале проверьте `/stats?resource_id=res-a-02` на порту 18091.
3. Другой согласующий → «Отклонить…» → «Отклонить заявку».
4. Ожидаются «Отклонена», автор решения и событие отклонения.
5. Срок ресурса и `operation_count` остаются прежними; POST-попыток нет.
6. Инициатор снова может создать заявку для этого ресурса.

## Помощник для проверки API из браузера

Откройте DevTools → Console **на вкладке http://localhost:8080**, после входа нужным аккаунтом. Не выполняйте код на странице дизайн-прототипа. Создайте помощник:

```js
async function renewalCommand(path, body = {}) {
  const csrfResponse = await fetch('/api/v1/auth/csrf', { credentials: 'same-origin' });
  const csrf = await csrfResponse.json();
  if (!csrfResponse.ok) return { status: csrfResponse.status, body: csrf };
  const response = await fetch('/api/v1' + path, {
    method: 'POST',
    credentials: 'same-origin',
    headers: {
      'Content-Type': 'application/json',
      'X-CSRF-Token': csrf.csrf_token,
    },
    body: JSON.stringify(body),
  });
  return { status: response.status, body: await response.json() };
}
```

Браузер сам отправляет Origin/cookie. После смены страницы Console может очищаться: при необходимости вставьте помощник снова. `RN-XXXX` в примерах заменяйте фактическим ID своей заявки; это не буквальный адрес.

## 7. Одна активная заявка и одновременное создание

1. Инициатор Alpha создаёт pending-заявку на свободный `res-a-03`.
2. В ресурсах вместо «Продлить» должна быть ссылка на активную заявку.
3. В Console повторите напрямую:

```js
await renewalCommand('/resources/res-a-03/renewals');
```

Ожидается **409 `active_renewal_exists`**, новая строка не появляется.

Для гонки возьмите свободный `res-a-04`:

```js
await Promise.all([
  renewalCommand('/resources/res-a-04/renewals'),
  renewalCommand('/resources/res-a-04/renewals'),
]);
```

Ожидаются один **201** и один **409**, в списке ровно одна новая заявка. Правило действует также для «Выполняется» и «Требует внимания», а не только pending.

## 8. Нельзя решить свою заявку

1. Войдите как `universal.alpha@renewaldesk.test` и создайте заявку на свободный `res-a-05`.
2. На странице заявки должно быть объяснение, что решение принимает другой согласующий. Кнопок approve/reject нет.
3. Проверьте серверные запреты, заменив ID:

```js
await renewalCommand('/renewals/RN-XXXX/approve');
await renewalCommand('/renewals/RN-XXXX/reject');
```

Оба ответа — **403 `cannot_decide_own_request`**. Статус, срок и история решения не меняются. Согласующий Alpha в другом профиле может принять решение.

## 9. Чужое пространство по известному ID

1. В профиле Alpha скопируйте адрес любой своей заявки.
2. В другом профиле войдите как инициатор Beta, вставьте этот адрес.
3. Ожидается **403 `workspace_forbidden`**, без содержимого заявки.
4. На той же вкладке Console:

```js
await (await fetch('/api/v1/resources/res-a-15')).json();
await renewalCommand('/resources/res-a-15/renewals');
await (await fetch('/api/v1/audit-events?resource_id=res-a-15')).json();
```

Ожидается `workspace_forbidden`; чужие ресурс/история не возвращаются. Попытки approve/reject/retry чужой заявки также должны вернуть 403, независимо от статуса.

## 10. Действия по роли

1. Инициатор Alpha видит создание, но не согласование/отклонение/retry.
2. Согласующий Alpha видит решения для чужой pending-заявки, но не создание.
3. В Console согласующего:

```js
await renewalCommand('/resources/res-a-06/renewals');
```

Ожидается **403 `role_forbidden`**. В Console обычного инициатора вызов `/renewals/RN-XXXX/approve` для собственной Alpha-заявки тоже возвращает `role_forbidden`. Скрытые UI-кнопки не заменяют серверный запрет.

## 11. Одновременные и повторные решения

1. Инициатор создаёт заявку на свободный `res-a-07`.
2. Другой согласующий открывает её и выполняет в Console:

```js
await Promise.all([
  renewalCommand('/renewals/RN-XXXX/approve'),
  renewalCommand('/renewals/RN-XXXX/approve'),
]);
```

Ожидается один **200** и один **409 `invalid_status_transition`**. В истории только одно согласование; после обработки только одно обновление срока.

На другой pending-заявке (например, `res-a-08`) выполните approve и reject через тот же `Promise.all`. Победить может любое решение: один 200, второй 409. Если победил reject, обращения к провайдеру нет; если approve — обычная обработка.

Повторный approve/reject уже завершённой или отклонённой заявки также даёт 409. Повторное нажатие не должно создавать новую задачу.

## 12. Следующее продление после завершения

1. Дождитесь completed на ресурсе из сценария 5.
2. Инициатор → «Ресурсы» → «Продлить» на том же ресурсе.
3. Ожидается новая заявка с **другим ID и ключом**, прежняя дата равна текущему сроку ресурса, новая = ещё +30 дней.
4. История ресурса содержит обе заявки. До согласования второй текущий срок не меняется.
5. После её согласования другим пользователем срок увеличивается ещё на 30 дней, статистика провайдера — ещё на 1. Это новая бизнес-операция, а не повтор старой.

## 13. Реальный рестарт после 503 — Core

Используйте свободный ресурс, например `res-a-11`. Не перезапускайте provider или PostgreSQL. Для удобства увеличьте задержку, пересоздав **только worker**:

```sh
RETRY_DELAY_MS=20000 docker compose -p renewaldesk-core up -d --no-deps --force-recreate worker
```

1. Создайте заявку инициатором и согласуйте другим пользователем.
2. Дождитесь сообщения о неподтверждённом результате, одной POST-попытки и времени следующей проверки. Скопируйте ключ операции.
3. До следующей проверки выполните:

```sh
docker compose -p renewaldesk-core stop api worker
docker compose -p renewaldesk-core start api worker
```

4. Дождитесь «Завершена». Ожидаются тот же ключ, одна POST-попытка и один сдвиг срока из снимка.
5. Проверьте прирост `operation_count` на 1. Саму операцию можно посмотреть так, вставив ключ из UI:

```sh
python3 - 'ВСТАВЬТЕ_КЛЮЧ' <<'PY'
import json, sys, urllib.parse, urllib.request
url = 'http://localhost:18091/renewals/' + urllib.parse.quote(sys.argv[1], safe='')
with urllib.request.urlopen(url) as response:
    print(json.dumps(json.load(response), ensure_ascii=False, indent=2))
PY
```

Ожидается `started_count: 1`, operation_id совпадает с UI. После дополнительного restart worker срок остаётся прежним.

Вернуть worker к значениям `.env`:

```sh
docker compose -p renewaldesk-core up -d --no-deps --force-recreate worker
```

Автоматическая повторяемая версия этого сценария: `make test-recovery`.

## 14. Три попытки → «Требует внимания» → retry в Core

Это управляемая проверка недоступного провайдера. Выполняйте, когда **нет других заявок «Выполняется»**: временный worker обрабатывает ту же Core-очередь. PostgreSQL и настоящий provider остаются работать; его память не сбрасывается.

1. Остановите обычный worker:

```sh
docker compose -p renewaldesk-core stop worker
```

2. Инициатор создаёт заявку на свободный `res-a-12`, другой согласующий одобряет. Пока worker остановлен, она остаётся «Выполняется».
3. Запустите временный worker с недоступным URL (сервис на порту 18099 внутри его контейнера отсутствует):

```sh
docker compose -p renewaldesk-core run -d --rm --no-deps \
  --name renewaldesk-core-fault-worker \
  -e PROVIDER_BASE_URL=http://127.0.0.1:18099 \
  -e PROVIDER_TIMEOUT_MS=500 \
  -e RETRY_DELAY_MS=1000 worker
```

4. Откройте заявку, дождитесь «Требует внимания», **3 из 3 · всего 3**, причины `attempts_exhausted`. Дата не меняется. В ресурсах новая заявка по-прежнему заблокирована; у инициатора кнопки retry нет.
5. Уберите временный worker и верните обычный:

```sh
docker stop renewaldesk-core-fault-worker
docker compose -p renewaldesk-core start worker
```

6. Согласующий → «Повторить обработку…» → подтвердить.
7. Ожидается тот же ID заявки и ключ, новый цикл. Сначала GET не найдёт операцию, затем нормальный POST/503/GET завершит её. На свежем сценарии итоговый счётчик **1 из 3 · всего 4**, операция провайдера только одна, срок обновлён один раз.

Если прервали сценарий, остановите временный контейнер (если он ещё есть) и выполните `docker compose -p renewaldesk-core start worker`. Не используйте для имитации отказа `docker stop provider`: это уничтожает его in-memory состояние.

## 15. Retry, когда провайдер уже выполнил операцию

Core-сценарий 14 создаёт операцию после восстановления связи. Отдельный случай — операция уже существует, но приложение ещё не знает результат.

В Demo откройте http://localhost:8081 в отдельном профиле, войдите согласующим Alpha и найдите **RN-0903** («Мониторинг инфраструктуры»), статус «Требует внимания». Запомните ключ и общий счётчик → «Повторить обработку…» → подтвердить. Ожидаются completed, прежний ключ и **неизменный общий POST-счётчик**: результат находится через GET, новая отправка не нужна.

Если RN-0903 уже завершили, seed её не сбрасывает. Повторяемая версия проверяется браузерным автотестом `attention manual retry` и интеграционными R04/R06. Управляемый сбой между подтверждением и записью в БД, stale lease и локальный mismatch проверяйте автотестами; кнопок подмены данных в обычном UI нет.

## 16. Поиск, фильтры, сортировки и история

1. Инициатор Alpha → «Ресурсы». Найдите `res-a-15`, затем `PostgreSQL`, затем заведомо отсутствующее название.
2. Ожидаются соответствующий ресурс / пустое состояние. «Сбросить фильтры» возвращает 15 ресурсов.
3. Выберите категорию «Базы данных» — остаются PostgreSQL и Redis. Снимите категорию.
4. Выберите «С активной заявкой», затем «Без активной заявки», затем «Все ресурсы»: список и счётчик меняются без ошибки 400.
5. Проверьте ближайший/дальний срок и стоимость по возрастанию/убыванию. Нажмите название — drawer показывает фактический текущий срок и историю со ссылками.
6. «Заявки»: поиск по ID, ресурсу и имени инициатора; все статусные фильтры; возврат на «Все»; сортировка старые/новые. Количество результатов должно соответствовать фильтрам.
7. «История операций»: отфильтруйте конкретный ресурс, тип события и период. У решения указан пользователь, у обработки — «Система», время и переход статуса. Ссылка открывает нужную заявку.
8. «Обзор»: KPI и последние записи должны соответствовать текущему Alpha. KPI ведут к спискам с правильным фильтром.

## 17. Ошибки и восстановление UI

**404:** после входа откройте http://localhost:8080/requests/RN-99999999 — ожидается 404 `request_not_found`. Если такой ID всё же существует, используйте другой отсутствующий числовой ID.

**400 и подмена суммы:** инициатор в Console:

```js
await renewalCommand('/resources/res-a-13/renewals', { amount_minor: 1 });
```

Ожидается 400 `validation_error`; новая заявка не создаётся. Сервер сам определяет автора, пространство, срок и стоимость.

**401:** выйдите и в Console выполните `await (await fetch('/api/v1/resources')).json()` — ожидается `unauthenticated`. Открытие страниц приложения ведёт на вход. Для проверки истечения активной сессии удалите cookie `renewaldesk_session` в DevTools → Application → Cookies; при следующем запросе/действии приложение должно вернуться на вход.

**CSRF:** после входа отправьте POST без заголовка CSRF:

```js
const response = await fetch('/api/v1/resources/res-a-14/renewals', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: '{}',
});
console.log(response.status, await response.json());
```

Ожидается 403 `csrf_invalid`, без новой заявки.

**Временная недоступность API:** на странице «Ресурсы» выполните в терминале `docker compose -p renewaldesk-core stop api`. После обновления списка ожидается карточка ошибки с «Повторить». Верните `docker compose -p renewaldesk-core start api`, нажмите «Повторить»: данные снова загружаются. Provider/DB/worker в этом сценарии не останавливаются. Полный список в отдельной вкладке при offline-режиме браузера также должен показывать понятное состояние ошибки.

## 18. Мобильная версия и клавиатура

1. В DevTools включите ширину **390 px** или сузьте окно. Ожидаются «Меню», карточки вместо широких таблиц и отсутствие горизонтального скролла страницы.
2. Откройте `res-a-08` с длинным названием: текст должен переноситься, кнопки и суммы не перекрываются.
3. Tab должен последовательно обходить ссылки/поля/кнопки с видимым фокусом. Enter/Space активируют кнопки.
4. Откройте создание или решение: фокус в диалоге, по умолчанию на «Отмена»; Tab/Shift+Tab не выходят наружу, Escape закрывает и возвращает фокус.

6. На медленном соединении видны загрузка и disabled-состояние отправляемой кнопки; двойное нажатие не создаёт две заявки.

## Проверки, для которых в UI нет кнопки имитации сбоя

Не меняйте вручную сроки и задачи Core в SQL ради проверки. В изолированной test-БД уже есть управляемые сценарии:

| Сценарий | Что должно быть доказано |
|---|---|
| Изменение срока/стоимости после создания, до согласования (B04) | 409 `resource_changed`, pending сохраняется, job не создаётся |
| Ошибка внутри транзакции согласования (B04) | Откатываются статус, job и audit вместе |
| Падение после reservation или внешнего эффекта, до записи ответа (R02) | После восстановления сначала GET, тот же ключ, без второго сдвига срока |
| Два worker / устаревший lease token (R03) | Устаревший worker не меняет статус/дату/audit |
| Некорректный 200, другой payload, 409 провайдера, timeout (R05) | Некорректное подтверждение не завершает заявку |
| Подтверждённая операция, но локальный ресурс не совпал (R06) | Attention, подтверждение сохранено, ресурс не перезаписан |
| Ошибка транзакции финализации (R06) | Все локальные изменения откатились, recovery завершает ровно один раз |
| Рестарт во время задержки (R07) | Сохранённое время проверки соблюдается, ранней отправки нет |

Один полный запуск: `make test-integration`. После него можно повторить конкретные сценарии (Docker/test-инфраструктура должна оставаться запущенной):

```sh
npm run test:integration -w apps/server -- --testNamePattern=B04
npm run test:integration -w apps/server -- --testNamePattern=R06
npm run test:integration -w apps/server -- --testNamePattern='R02|R03|R05|R07'
```

Ожидайте `PASS`; несовпавшие тесты будут помечены skipped — это нормально для фильтрованного запуска. Не запускайте эти команды параллельно с другими integration/browser тестами.

## Автотесты

В терминале из корня проекта; Docker Desktop должен работать:

```sh
nvm use
# Только если зависимости ещё не установлены:
npm ci
```

Или установите браузер Playwright и используйте стандартный путь:

Отдельные проверки:

| Команда | Что проверяет |
|---|---|
| `make test` | Unit-тесты дат, бизнес-правил и валидации ответа провайдера |
| `make test-integration` | Реальная PostgreSQL, HTTP API, права, гонки, транзакции, worker, fault/retry, настоящий restart |
| `make test-recovery` | Только сценарий SIGKILL/restart с сохранением DB/provider |

| `make typecheck` | Проверка типов |
| `make build` | Production-сборка обоих приложений |

Успех: команды завершаются с кодом 0, тесты показывают `passed`. На последнем проверенном состоянии: 44 unit, 44 integration, 8 browser tests. `make verify` последовательно выполняет lint, typecheck, build, unit, integration и browser; отдельный `make test-recovery` после него не обязателен — restart уже входит в integration.

Тесты явно очищают только отдельную test-БД. Core/Demo не очищаются. Integration и browser не запускайте одновременно: они используют одну test-БД.

Скриншоты находятся в `apps/web/test-results/`; trace сохраняется при сбое. Техническая матрица — [testing.md](testing.md), результаты реализации — [progress.md](progress.md), ручной сценарий 503 → restart — [README](../README.md#надёжность-и-перезапуск).

## Предупреждение Jest о незавершённых операциях

`Jest did not exit one second after the test run has completed` означает, что после тестов остался открытый асинхронный ресурс. Статус `passed` относится к проверкам, но завершение процесса тоже нужно проверить. Убедитесь, что используете Node 22 (`nvm use`).

Диагностика интеграционного набора из корня проекта:

```sh
npm run test:integration -w apps/server -- --detectOpenHandles
```

В тестах нужно читать или отменять тело каждого HTTP-ответа и закрывать серверы/БД в cleanup. В частности, чтение только `response.status` не освобождает автоматически поток ответа большого статического asset. Принудительный выход Jest не заменяет освобождение ресурсов.
