# RenewalDesk — как посмотреть и проверить проект

RenewalDesk помогает сотрудникам согласовывать продление ресурсов: один сотрудник создаёт заявку, другой принимает решение. Срок меняется только после подтверждения внешнего сервиса.

Все данные и аккаунты вымышленные. Для знакомства с проектом достаточно браузера. Если приложение ещё не запущено, инструкция для запуска находится в конце документа.

## 1. Открыть приложение и войти

Основное приложение: **http://localhost:8080**.

Для проверки понадобятся два аккаунта. Пароль у обоих — **`demo1234`**.

| Аккаунт | Что может делать |
|---|---|
| `initiator.alpha@renewaldesk.test` | Создавать заявки |
| `approver.alpha@renewaldesk.test` | Согласовывать и отклонять заявки |

Чтобы сменить аккаунт, нажмите «Выйти» и войдите под другим. В мобильной версии выход находится в «Меню».

В пространстве Alpha доступно **15 ресурсов**. На новом стенде заявок пока нет — они появятся при проверке. Если проект уже смотрели, созданные заявки и изменённые сроки сохраняются.

## 2. Создать заявку

**Кто:** инициатор — `initiator.alpha@renewaldesk.test`.

1. Откройте «Ресурсы».
2. Найдите «Хранилище A» и нажмите «Продлить».
3. В диалоге проверьте стоимость и новый срок: он должен быть на 30 дней позже текущего.
4. Нажмите «Создать заявку».

**Ожидаемый результат:** открылась заявка со статусом «На согласовании». В истории указано, кто её создал. Срок самого ресурса пока не изменился.

На исходных данных даты будут **01.03.2027 → 31.03.2027**. Если ресурс уже продлевали, новая дата рассчитывается от его текущего срока.

Сохраните адрес страницы заявки — он пригодится при смене аккаунта.

## 3. Согласовать и дождаться результата

**Кто:** согласующий — `approver.alpha@renewaldesk.test`.

1. Выйдите из аккаунта инициатора и войдите согласующим.
2. Откройте сохранённую заявку или найдите её в «Заявки на продление».
3. Нажмите «Согласовать…». Проверьте сведения и подтвердите решение.
4. Дождитесь завершения обработки.

**Ожидаемый результат:** статус меняется с «На согласовании» на «Выполняется», затем на «Завершена». Срок ресурса увеличивается ровно на 30 дней, в истории видны решение и результат.

Во время обработки может появиться сообщение, что результат ещё не подтверждён. Это предусмотренный сценарий: система уточняет результат у внешнего сервиса. Обычно достаточно подождать несколько секунд; на стенде с увеличенной задержкой — около 20 секунд.

Обновите страницу: дата не должна увеличиться повторно.

## 4. Отклонить другую заявку

1. Войдите инициатором и создайте заявку для «Сервис B».
2. Запомните текущий срок ресурса.
3. Войдите согласующим, откройте эту заявку и нажмите «Отклонить…».
4. Подтвердите решение.

**Ожидаемый результат:** заявка получила статус «Отклонена». Срок ресурса остался прежним, решение видно в истории. После отклонения для этого ресурса можно создать новую заявку.

## 5. Проверить защиту от ошибочных действий

| Что сделать | Что должно произойти |
|---|---|
| Попробовать создать ещё одну заявку на ресурс, у которого уже есть активная заявка | Вместо повторного создания доступна ссылка на существующую заявку |
| Открыть согласование или отклонение и нажать «Отмена» | Статус и срок остаются прежними |
| Открыть завершённую или отклонённую заявку | Повторно принять решение нельзя |
| После завершения создать следующее продление того же ресурса | Создаётся отдельная заявка ещё на 30 дней |

Если выбранный ресурс уже занят активной заявкой, для нового сценария возьмите другой свободный ресурс.

## 6. Проверить разграничение доступа

Для этих проверок есть ещё два аккаунта. Пароль — **`demo1234`**.

**Свою заявку нельзя согласовать самостоятельно.**

1. Войдите как `universal.alpha@renewaldesk.test` — у него есть обе роли.
2. Создайте заявку на свободный ресурс.
3. Откройте её.

**Ожидаемый результат:** нет действий согласования и отклонения; показано объяснение, что решение должен принять другой сотрудник.

**Пользователь другого пространства не видит чужие заявки.**

1. Скопируйте адрес любой заявки Alpha.
2. Войдите как `initiator.beta@renewaldesk.test`.
3. Откройте скопированный адрес.

**Ожидаемый результат:** сообщение об отсутствии доступа. Содержимое заявки не показывается. В разделе «Ресурсы» этому аккаунту доступны только 3 ресурса Beta.

## 7. Посмотреть интерфейс и историю

- В «Обзоре» проверьте количество ресурсов и заявок в разных состояниях.
- В «Ресурсах» попробуйте поиск, категории и сортировку. Нажмите название ресурса, чтобы посмотреть сведения и историю.
- В «Заявках на продление» переключите фильтры статусов и найдите созданную заявку по её номеру.
- В «Истории операций» найдите свои действия: кто создал заявку, кто принял решение и чем закончилась обработка.
- Введите отсутствующее название в поиске: должно появиться понятное пустое состояние. Сбросьте фильтры.
- Откройте проект на узком экране: меню, карточки и основные действия должны оставаться удобными.

## 8. Посмотреть повторную обработку

Для этого удобнее дополнительный демонстрационный стенд: **http://localhost:8081**. Он содержит заранее подготовленную историю и разные состояния заявок.

1. Войдите согласующим Alpha: `approver.alpha@renewaldesk.test`, пароль `demo1234`.
2. Найдите заявку **RN-0903**, «Мониторинг инфраструктуры», со статусом «Требует внимания».
3. Откройте её, нажмите «Повторить обработку…» и подтвердите.
4. Дождитесь завершения.

**Ожидаемый результат:** продолжается обработка той же заявки; она завершается, срок обновляется один раз.

Если эту заявку уже проверяли, она может быть завершена. Повторный запуск стенда не сбрасывает результаты предыдущих действий. Demo и основное приложение лучше открывать в отдельных профилях браузера, чтобы входы не заменяли друг друга.

## Что считать успешной проверкой

- Заявку создаёт инициатор, а решение принимает другой сотрудник с нужными правами.
- Согласованная заявка завершается и меняет срок ровно на 30 дней.
- Отклонение не меняет срок ресурса.
- Повторные действия не создают дубликаты и не продлевают ресурс ещё раз.
- Чужие данные недоступны, а собственную заявку нельзя согласовать самому.
- Результаты и авторы действий видны в истории.

Подробные проверки восстановления после сбоя, одновременных действий и ошибок: [расширенные сценарии](docs/manual-testing.md). Их можно пройти вместе с разработчиком.

## Запуск — для того, кто готовит стенд

Нужны запущенный Docker, Node.js 22.21.1, npm и `make`. Команды выполняются из корня репозитория:

```sh
npm ci
make env
make up
```

**Миграции и сидеры запускаются автоматически при `make up`. Вручную выполнять их не нужно.**

Порядок запуска: сборка → запуск БД → миграции → сидеры → API и обработчик → сайт. Если миграции или сидеры завершатся с ошибкой, приложение не продолжит обычный запуск.

Повторный запуск применяет только новые миграции и добавляет недостающие начальные записи. Ваши заявки, история и изменённые сроки сохраняются.

После запуска откройте http://localhost:8080.

Демонстрационный стенд:

```sh
make demo
```

После запуска он доступен на http://localhost:8081.

Если основное приложение уже использовалось, для собственной проверки с исходными данными можно поднять отдельный стенд, сохранив текущие данные:

```sh
sh scripts/init-env.sh .env.review \
  DATASET=core WEB_PORT=8082 APP_ORIGIN=http://localhost:8082 \
  PROVIDER_PUBLISH_PORT=18093
COMPOSE_BAKE=false docker compose --env-file .env.review \
  -p renewaldesk-review up -d --build --wait
```

На первом запуске этого отдельного стенда будут исходные сроки и пустой список заявок. Адрес — **http://localhost:8082**. Повторный запуск сохраняет результаты проверки.

## Автоматические проверки — для разработчика

```sh
npx playwright install chromium
make verify
```

Проверяются код, сборка, бизнес-правила, доступ, работа БД, восстановление после сбоя и действия в браузере. Последние результаты: **33 unit-теста, 44 интеграционных и 8 браузерных — прошли**. Тестовые данные отделены от обычного приложения.

Команды по отдельности и альтернативный запуск с установленным Chrome: [README](README.md#проверки-и-разработка). Результаты и известные ограничения: [docs/progress.md](docs/progress.md).
