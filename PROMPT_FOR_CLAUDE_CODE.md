# Первый промпт для Claude Code (скопировать целиком)

Ты — Senior Fullstack Engineer и hands-on Tech Lead. Реализуй RenewalDesk, практическое Fullstack-задание fintech-компании, в текущем репозитории. Цель — реально работающее, безопасное и воспроизводимое приложение, а не макет или набор незавершенных примеров.

1. Прочитай `CLAUDE.md`, `spec.md`, `docs/implementation-plan.md`, `docs/progress.md` и все связанные спецификации из `docs/`. Изучи оригинал `references/company/task.pdf` (включая визуальный референс на стр. 6), оригинальный `provider_simulator.py`, `references/design/README.md`, утвержденный HTML и скриншоты. Если не можешь прочесть PDF, используй доступный локальный инструмент и сообщи, что именно было недоступно; не выдумывай содержание.
2. Проверь состояние репозитория и локальных инструментов. Кратко зафиксируй реализационный план, версии зависимостей, границы модулей и риски. Создай или уточни существующие `spec.md` и `CLAUDE.md` только дополнениями, если обнаружены необходимые детали; не заменяй утвержденные правила. Веди `docs/progress.md` и ADR. Перед каждым новым этапом и при потере контекста возвращайся к этим файлам.
3. Начни реализацию с этапа 1 (scaffold/Docker/DB), затем последовательно выполняй этапы из `docs/implementation-plan.md`. Не останавливайся на одном планировании. Делай небольшие проверяемые изменения, не переходи к следующему этапу, если критические проверки текущего не проходят. Если среда не позволяет запустить Docker/браузер, опиши конкретный блокер, продолжи безопасные части и оставь точные команды для ручной проверки; не выдавай непроверенное за успешное.
4. Обязательный стек: NestJS, TypeScript, PostgreSQL, Sequelize ORM (sequelize-typescript), миграции и seeders, React + TypeScript + Vite, OpenAPI через @nestjs/swagger, Stoplight Elements и Swagger UI, Docker и Docker Compose, отдельный worker на той же backend codebase, предоставленный Python-провайдер отдельным контейнером, Jest/Supertest/Playwright, Markdown/ADR, GitHub Actions. Все внешние JSON и query поля в snake_case. PostgreSQL durable jobs, без RabbitMQ в этой версии.
5. Приоритет: корректность основного сценария и безопасность, затем весь утвержденный frontend. Обязательны реальные PostgreSQL constraints/transactions, конкурентное создание/согласование, стабильный idempotency_key, неизменяемый payload, lease и fencing, восстановление после 503 и падения worker/API, финализация одной транзакцией, точные 401/403/409, изоляция Alpha/Beta, Core и Demo datasets. Не копируй localStorage-псевдобэкенд из HTML; дизайн и пользовательские сценарии перенеси в реальные React-компоненты с API.
6. Выполняй тесты, а не только пиши их. Реальный Python-симулятор использовать для основного сценария; fault injection — отдельный test-only stub/proxy. Проверка рестарта должна действительно останавливать/перезапускать worker и API с сохранением PostgreSQL и процесса provider. Не изменяй оригинал провайдера, не сбрасывай БД или provider без явной команды, не используй реальные аккаунты, не добавляй секреты. Не используй `sequelize.sync({ alter: true })` или `force` вместо миграций.
7. Перед завершением подготовь README с проверенными командами, API-контрактами, учетками, схемой состояний, инструкцией для воспроизведения 503 → restart → GET → completed и проверкой operation_count/started_count. Обнови документацию, укажи результаты тестов, незавершенные пункты, ограничения и архитектурные компромиссы. Не обещай exactly-once для произвольных внешних API. Не утверждай, что production ready, если проверена только часть.

Начинай прямо сейчас: прочитай материалы, проверь репозиторий, запиши этап 0 в progress.md и приступай к scaffold. При несущественных неоднозначностях выбирай простое решение и записывай его в ADR. Не расширяй scope за пределы спецификации. Если находишь существенное противоречие или нужен разрушительный шаг — остановись и объясни владельцу варианты.
